## 交付内容

1. `src/visual_qa/report.rs`：K01 验收报告 v1 契约。
   - `CheckStatus` 只有 `pass`、`fail`、`skipped`、`not_run` 四个稳定 wire value；非 pass 项必须给原因。
   - `execution_status` 只说明本轮请求场景是否完成；`release_status` 只聚合 `required_for_release` 项，优先级为 fail → not_run → skipped → pass，空检查集合也是 not_run。
   - 每个检查含稳定 ID、可读标签、发布必要性、状态、原因和相对 run root 的证据路径；反斜杠、绝对路径、空 kind 与重复 ID 会被结构校验拒绝。
   - 状态计数由 checks 计算并复核，不能手写一个与明细不一致的“通过数”。
2. `visual_qa` 真实接入：每轮结束在 `target/visual-qa/<commit7>/<run>-acceptance.json` 输出汇总。
   - 当前自动检查场景 manifest/metrics、原始抓图、CPU 样本、能力报告、统一诊断和渲染清单是否存在。
   - GPU pass 计时在支持 timestamp 的本机明确为 `not_run`（K03 未实现）；不支持 timestamp 时为 `skipped` 并要求 K03 提供替代测量，绝不记作 pass。
   - K02 集成回归、K04 冷安装/许可和 K05 人工审稿在交付前均显式为 `not_run`，因此普通 QA 成功不会误报发布通过。
3. 受版本控制的机器契约：
   - `docs/art-overhaul/schemas/acceptance-report-v1.schema.json`：JSON Schema Draft 2020-12，限制 report kind、状态枚举、必需字段、证据路径和非 pass 原因。
   - `docs/art-overhaul/examples/K01-acceptance-report-v1.json`：同时包含 pass/skipped/not_run 的示例，单测会反序列化并执行运行时结构校验。
4. README 与 06 证据目录已补充真实输出文件、schema 和状态语义；`task-index.json` 只将 K01 标为 review，未提前修改 K02–K06。
